VLA 训练如何一步步提速：以 Pi0.5 为例的 3 倍加速实践

2026-10-19 · LoongForge 团队
GitHubhttps://github.com/baidu-baige/LoongForge
知乎原文https://zhuanlan.zhihu.com/p/2095555587304117777

最近我们在 LoongForge 上完成了 Pi0.5 的 SFT 加速训练。

优化开始之前，原本认为：3.5B 的模型、762 的序列长度，看上去用不了多少 trick。但实际优化下来，发现可以细化的地方很多。

最终 bf16 下吞吐做到 24.0 samples/s（社区实现的 2.63 倍），FP8 下吞吐达到 27.34 samples/s（社区实现的 3.00 倍）。

1. 冗余的 256 序列长度：空相机 slot 裁剪

Pi0.5 的序列结构比较特殊，包含图像、文本指令和 action 三部分。为了理清 ViT 与主干 Attention 各自的计算负载，优化前先对各分支的序列长度做了分解。

按两路相机的 LIBERO 数据推算，图像（2×256）、指令与 action（50）拼起来的联合序列本应是 762，但实际 debug 出来的序列长度却是 1018，平白多出了 256 的无效 padding。

排查发现，openpi 的 Pi0.5 输入固定 3 个相机 slot。当输入只有 2 路相机的时候，也会默认给缺的那路填一张占位图，再把 image mask 置为 False。

然而这个 mask 只是让这 256 个 token 在注意力里不可见，实际的计算一点没少：占位图依旧需要计算 SigLIP，产出的 256 个 token 也得过 18 层 decoder layer，中间的激活值照样保存，哪怕它们既不会被有效 token 注意到，也不参与最终的 loss 计算。

因此，LoongForge 在数据侧改为按需分配（将 data.num_images 设为实际相机数），只为真实存在的相机输入生成 slot；对于原本的 pad token，不推进 position_ids。裁剪后有效 token 的位置编码和可见范围不变，loss 与裁剪前严格一致，但直接省去了约 25% 的计算量和相应的激活值显存占用。

2. 密集的细碎算子开销：torch.compile 加速

通过 profile 发现，Pi0.5 每层除了几颗大 GEMM，剩下全是小算子（尤其是 hidden size 较小的 action expert），包括 adaRMS 归一化、RoPE、两个分支 Q/K/V 的拼接与切回、gelu·up、门控残差。

在 eager 模式下，每个小算子都会触发一次独立的 kernel 启动，中间结果常驻显存。以 adaRMS 为例，cast 到 fp32、平方、求均值、rsqrt、chunk 出 scale/shift/gate、cast 回 bf16，每一步都产生一个完整大小的中间张量。

因此我们考虑用 torch.compile 加速。但 Pi0.5 是比较动态的模型，不能对整个模型直接 compile：

  • vision tower 是动态的，跟着图像数量走。 embed_prefix 用 for 循环逐张图过 SigLIP，循环次数取决于数据集的相机数；每张图的 pad mask 和块起始标记也是在 Python 里按图像数动态拼好，再通过 torch.tensor 搬到 GPU 上，直接编译极易触发断图或重编。
  • ViT 的耗时占比没有那么高，编它的收益相对有限。两路图像过 SigLIP 只占前向的 20%，18 层 decoder layer 占近 80%。

因此，我们让 Pi0.5 的 vision tower 和 prefix 拼接部分保持 eager，只局部编译后面形状固定的 backbone（paligemma_with_expert）。开启 torch.compile 之后，Inductor 主要做了三类融合：

  • 逐元素 + 归约融成一颗 kernel：adaRMS 整串操作融成一颗 persistent reduction kernel，均值和 rsqrt 单趟算完；残差加和 post_attention_layernorm 也融在一起。
  • 小算子融进 GEMM：adaRMS 的调制和类型转换被吃进 q_proj 的 Triton GEMM，归一化结果不用单独落一次显存。
  • RoPE 整段折叠：cos/sin 表的构造（广播乘、cat、cos/sin、cast）融成一颗 kernel，q * cos + rotate_half(q) * sin 融成一颗，可以跑到显存带宽上限。

经过局部编译后，训练吞吐提升了 54%。

3. 意外的显存收益：FlexAttention 压激活值

从 LLM 的惯性思维出发，我们最开始看的是 Pi0.5 的 Attention 部分。但 profile 发现，与普通的 LLM 不同，Pi0.5 的 attention 在端到端里的耗时占比并不高：序列长度只有 762，attention 计算在 decoder layer 内占比约 13%，剩下主要是 MLP，约占 76%。折到端到端，attention 前向只占约 2.8%，计算耗时的优化空间很小。

不过 profile 过程中发现，它的激活值多、算子碎。eager 实现每层先用 repeat_kv 把唯一的 KV 头复制成 8 份，再物化完整的 [B, 8, T, T] 概率矩阵；乘 scale、加 mask、两趟 softmax、PV、transpose 回去，每一步都是独立的 kernel，中间结果反向时都得留着，softmax 还会多存一份 fp32 中间结果。即使在 torch.compile 包裹下，激活值的开销也没有显著降低。

另一方面，Pi0.5 的掩码天然适合块稀疏（Block-Sparse）的 attention：

  • prefix（图像 + 文本）内部完全双向，但看不到 action，右上角整块屏蔽；
  • action 能看到全部有效 prefix，50 个 action token 之间也互相可见；
  • pad 所在的行和列整体屏蔽。

掩码里大片区域要么全可见、要么全屏蔽，正好对上 FlexAttention 的 BlockMask：按 128×128 的 tile 描述掩码，整块屏蔽的 tile 直接跳过，只有边界上的 tile 才逐元素判断。

替换为 FlexAttention 后，enable_gqa=True 让 KV 头在 kernel 内广播，不再复制；反向只存输出和 logsumexp。速度和 eager 差不多（±2%），在端到端上区别不大，但 micro batch size 为 32 时每层少存约 0.63 GiB，18 层合计约 11 GiB。

4. 选择性重计算

openpi 默认开启全量重计算：视觉塔、18 层 decoder layer、embedding 以及 action/time 投影的激活值一律不存，反向传播时全部重算一遍前向。

在 LoongForge 框架下，叠加 torch.compile 和 FlexAttention 之后，激活值显存占用已经大幅度下降，但想要对齐官方的 batch size，还是需要开启重计算。

问题就变成了：只重算哪一部分最划算？我们按模块逐个测算了重计算的"性价比"（即每省 1 GiB 激活需要多花多少毫秒）：

  • ViT（SigLIP 27 层）：2.8 ms/GiB，+48.5 ms 换 17.5 GiB。ViT 的 hidden 窄（1152 vs Gemma 的 2048），同样的 FLOP 产生的激活最多，重算最便宜。
  • PaliGemma MLP：4.0 ms/GiB，激活最大（37.6 GiB），但要 +150 ms。
  • Attention（norm + QKV + RoPE + FlexAttention）：7.8 ms/GiB，18 层只存 5.5 GiB。MQA 的 K/V 很小，FlexAttention 也不存 score 矩阵，可重算要把 QKV 投影和 attention 前向再跑一遍。激活小、算得贵，最不划算。
  • Gemma Expert MLP：只处理 50 个 action token，18 层合计 0.7 GiB，重不重算都在噪声里。

最终我们选择只重算 ViT（通过 LoongForge 框架的 --activation-checkpoint-module-patterns 仅匹配 SigLIP 层），把重算开销降到了最低。

5. 无 NVLink 场景下的通信瓶颈：分层编译隐藏梯度 AllReduce

NVLink 场景下梯度通信通常不是瓶颈，但在我们实际训练的场景下，PCIe 通信代价高昂：Pi0.5 的 3.5B 参数的 bf16 梯度约 7 GB，ring AllReduce 每卡需要传输 12.25 GB，通信耗时高达 220 ms。

然而 profile 发现，由于一开始把整个 backbone 用 torch.compile 编成一张图，Inductor 生成的反向是一个整体的 autograd Function，这导致所有参数梯度在反向结束时才同时 ready，DDP 梯度桶只能串行排在反向之后，每步有高达约 215 ms 的通信开销完全暴露。

5.1 DDPOptimizer + torch.compile 的预期用法：包住整个模型，和通信一起调度

这个问题 PyTorch 官方早就遇到过，其核心思路是：编译器看到的范围越大越好——最好将整模型甚至整步训练交给它，由其统一调度梯度通信的时机与计算重叠。

  • DDPOptimizer（PyTorch 2.0 起，默认开启）：对 DDP 包住的模型调用 torch.compile 时，Dynamo 会顺着 DDP bucket 的大小将前向图切段分别编译，从而让反向梯度分批就绪。

但它的前提是模型能被完整抓成整图。

5.2 局部 compile 与 DDPOptimizer 不兼容

前面提到，Pi0.5 特殊的 ViT 结构决定了它无法对整个模型直接 torch.compile；只编 backbone，意味着要在 DDP 内部对子模块显式 torch.compile，这时 DDPOptimizer 会崩：

  • 现象：清空编译缓存后第一次启动必挂，报 BackendCompilerFailed，最终是 FakeTensor 上访问了 data_ptr()；不清缓存直接重启又能跑。很有迷惑性，一度以为是 autotune 或 CUDA Graph 的问题。
  • 根因：
    • DDPOptimizer 在外面又套了一层，形成嵌套编译。DDPOptimizer 编译下一段子图前，会在 FakeTensorMode 下执行上一段已编译的子图来拿输出的 shape/stride，而里层 compile 的 AOTAutograd runtime wrapper 不知道自己处于 FakeTensorMode，会走真实的 autograd.Function.apply，碰到 FakeTensor 的 data_ptr() 就挂。
    • 热缓存能跑，只是因为命中 FX graph cache 绕开了这条路径，换个 shape、换个 rank 数或者清一次缓存就会复现。

所以只能先关掉它（--no-dynamo-optimize-ddp）。代价正如前面所分析的：由于无人帮忙切图，整张反向图跑完后梯度才能 ready，通信完全暴露出去了。

5.3 自行分层编译，手动切图

既然整图编译无法实现、DDPOptimizer 又无法使用，干脆就在 backbone 内部自己动手切图。

我们将编译策略改为 multi_group 分组编译：18 个 decoder layer 各自作为一个独立的编译单元（相同 shape 只需编译一次，其余 17 层直接复用），同时将 final norm、action 输入投影 + time MLP、action 输出投影各自独立成小图。

这样一来，每一层的反向都成为了独立的 autograd.Function：当第 N 层的反向一结束，它的梯度桶就能立刻发起 AllReduce，与第 N-1 层的反向计算并行重叠。

本质上，这相当于手动实现了 DDPOptimizer 想做的事，只是将切分点精准锁在了层边界上，完全摆脱了对 DDPOptimizer 的依赖。改用手动分层编译后，暴露的通信基本消失，吞吐 +10%。

7. 极致 FP8 计算优化

到这里，bf16 下能抠的性能基本已经见底。接下来，我们将 Pi0.5 中的 Linear 模块全面推进到 FP8 计算：输入与权重量化为 FP8 后执行 GEMM，结果按 scale 还原，计算前后保持 bf16。

7.1 TransformerEngine 的 FP8 尝试

最先尝试的是 TransformerEngine 的 FP8 方案：把 nn.Linear 换成 te.Linear，前向套上 fp8_autocast。但真正的问题是它和前面的优化冲突：

  • 和 torch.compile 冲突，到处断图。
    • TE 内部有被 @torch.compiler.disable() 装饰的函数（fp8 元数据和 amax 处理）。
    • Dynamo 于是在每个 te.Linear 处断图，218 个 Linear 就是 200 多处断图，Linear 前后的 adaRMS、gelu·up 这些融合也接不到 GEMM 上了。
  • 断图直接推高激活值显存占用。
    • 整图时 AOTAutograd 把前向和反向放在一起切分，adaRMS、gelu·up、RoPE、残差这类便宜的逐元素算子会留到反向重算，只存少量张量。
    • 断图之后一层被切成好几段，Linear 的输入必须真实写到显存里，Linear 自己再为反向存一份，前后两段之间也没法跨段重算。18 层累加下来多了约 13 GiB。

所以 TE 的 FP8 GEMM 本身没问题，但放进 Pi0.5 这条以 torch.compile 为核心的优化路径里，断图和多出来的显存把收益吃掉了，很容易导出负收益。

7.2 TorchAO 的 FP8 方案

TE 的问题在于断图，那就找一个能留在编译图里的 FP8 方案。于是我们考虑 TorchAO，使用 tensorwise recipe。

TorchAO 的 Float8Linear 的 amax、scale、cast 都是普通的 PyTorch 算子，GEMM 走 torch._scaled_mm，在 Dynamo 下能直接建图。

实测显存反而比 bf16 更省。我们推测原因是：Float8Linear 的 autograd Function 本身写的是为反向保存 bf16 输入，但它在编译图里，partitioner 看得到反向拿这份输入只是重新 cast 成 FP8 再算 wgrad，于是改为直接存 FP8 版本加一个 scale，这部分激活减半。

至于哪些 Linear 走 TorchAO FP8，分两层筛选：

  • 静态规则：
    • 458 个候选里，精度敏感的模块（vision_tower、multi_modal_projector、action/time 投影）保留原精度，跳过 204 个；
    • 再按 fp8-min-dim=2048 去掉 36 个小 Linear，它们的 GEMM 太小，量化开销比 FP8 省下的时间还多。
  • trace 验证：
    • 用 Kineto trace 把每个 GEMM 按 shape 归回模块，对比 bf16 与 FP8 的实测 kernel 耗时，只留确实变快的；
    • PaliGemma MLP 和 attention 投影都快了 1.8–2.0 倍；2 个训练中不会执行的 lm_head 被排除，最终保留 216 个。

最终 GEMM 在单步中的占比从 54% 降到 33%，吞吐在 bf16 的基础上再提升 13.9%，做到 27.34 samples/s，是社区实现的 3.0 倍。

精度上，与 bf16 对比，loss 的 Pearson 相关系数为 0.9997，平均相对误差 0.56%。
