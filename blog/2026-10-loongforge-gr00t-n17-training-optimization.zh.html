前言

大语言模型和视觉语言模型的训练通常具有相对清晰的优化主线：将文本转换为 token，将主要计算组织为规则的 Transformer block，再围绕矩阵乘、显存访问和集合通信进行优化。但 VLA（Vision-Language-Action）并非语言模型与动作预测模块的简单组合，一次训练迭代需要同时处理多路相机视频、语言指令、机器人状态和连续动作，并依次经过视觉编码器、语言模型与动作生成网络。对 GPU 而言，这是一张计算图；但对训练后端而言，则是一套横跨视频解码、动态多模态序列、异构模型结构和分布式更新的复杂系统。

GR00T-N1.7 具备上述典型特征：模型规模约为 3.1B，训练时冻结 Backbone，仅更新 Action Head。该策略减少了反向计算，但也形成了不对称负载——Backbone 承担多模态前向，Action Head 负责前反向与参数更新，数据处理和跨卡通信则分布于训练迭代的不同阶段。

面对这种复合负载，单一优化手段难以达到理想效果。因此，优化工作的首要任务是准确刻画当前训练配置下 GR00T-N1.7 单次迭代的时间分布，并识别影响训练效率的关键瓶颈。本文将相关优化归纳为三个层面，并分别讨论其形成机制与实现路径：

  1. 数据供给优化：修复重复视频解码，并通过 shard 异步预取使数据处理与 GPU 计算稳定衔接；
  2. 模型计算优化：消除冻结 Backbone 中的动态 metadata、冗余输出和高频小算子开销；
  3. 训练执行与分布式优化：通过 CUDA Graph、跨迭代流水与梯度访存优化减少执行碎片。

这三条主线分别对应数据、计算、执行三个层面，最终将训练吞吐提升至原始实现的 1.79 倍。

1. 瓶颈定位：训练耗时集中于冻结 Backbone 与碎片化执行

GR00T-N1.7 是典型的 Vision-Language-Action 结构。输入图像和文本先经过 Qwen3-VL Backbone，得到视觉—语言特征，随后 Action Head 使用 flow matching 与 32 层 DiT 预测机器人动作。官方社区训练配置冻结 Backbone，只训练 Action Head。在保持训练配置相同的口径下，我们测得 NVIDIA Isaac-GR00T 社区 DDP 实现的训练吞吐存在异常抖动（如图 1）。

该现象源于 Isaac 数据层对同一条 episode 缺乏去重机制：当一条 episode 被切分为 10 个 split 并分散至不同 shard 时，由于没有去重缓存，该 episode 会被完整解码最多 10 次，进而产生大量 FFmpeg 原生线程。当多个 rank 的多个 worker 消费节奏一致时，会同时触发解码，导致数十个解码线程与训练主线程争抢 CPU 时间片。这使负责发起 GPU kernel launch 的训练主线程遭受调度延迟，GPU 侧无法及时收到下一批指令，最终表现为吞吐量的忽高忽低。

结合表 1 可以发现，训练迭代的主要耗时集中在 Forward + Backward 阶段。通过 Profiler 进一步观察，Forward 阶段内存在 GPU Idle（如图 2 所示），并伴随 RoPE、pointwise 及 layout/cat 等小算子；同时，Backbone 默认 forward 每步仍会计算 lm_head 大矩阵，但此处实际只需要 VLM 的特征，lm_head 的计算结果并未被后续使用，因此该步属于冗余计算。

2. 数据供给优化：消除重复解码并建立异步预取

2.1 DataLoader 抖动背后的 episode 重复解码问题

机器人数据以 episode 为单位存储元数据：一个 episode 包含连续视频、状态和动作，而训练采样的单位是其中某个 step。分析社区实现后发现，其分片索引与底层数据集索引之间缺少稳定的对应关系，导致不同采样项可能反复命中并完整解码同一 episode。每次视频解码都会启动 FFmpeg 相关线程；当多个 DataLoader worker 并发执行重复解码时，大量解码线程占用 CPU 调度资源，导致训练主线程无法及时向 GPU 下发 kernel，最终在 GPU 时间线上形成空闲区间，并造成 step time 明显波动。

如图 3 所示，优化重点并非继续增加 worker 数量，而是重新建立训练样本与原始 episode 之间的索引关系。具体而言，首先遍历全部 episode，并依据 action horizon 过滤末尾无法构成完整动作序列的 step，为每个有效训练样本建立唯一定位信息；随后沿用社区已有的 episode 分组与 shard 负载均衡策略，在 worker 消费 shard 时通过该定位信息读取正确的样本位置。该方案不改变原有采样语义和数据分布，同时避免重复查找、解码同一 episode 以及重复构造局部索引。

2.2 通过异步预取隐藏后续 shard 的准备开销

索引修复避免了无意义的重复解码，但 shard 的准备本身仍然需要时间。为此，我们使用有界线程池异步构造后续 shard：当前 shard 被 DataLoader 消费时，预取队列并行准备后面的 shard；消费完成后，从队首取得已经构造好的结果，再补入一个新任务。这一机制包含两个影响正确性与稳定性的关键设计：

  • 每个预取线程持有独立的浅拷贝 dataset，并重置 episode cache 与 decoder 状态。否则多个线程共享视频 decoder，容易在并发读取时破坏缓存一致性。
  • 图像增强等随机变换不能由并发线程独立生成随机数。否则，线程完成顺序的变化会导致同一 seed 下的数据增强序列发生偏移，进而破坏精度对齐。

为此，我们先按训练消费顺序生成 transform replay 参数，再将确定的 replay 交由预取线程执行（如图 4）。这样，异步机制仅改变执行时序，不改变随机语义。

3. 模型计算优化：减少冻结 Backbone 的冗余开销

通过插桩观察 GR00T-N1.7 完整训练 step 的 Profiler，发现 GPU 时间线上存在两段显著的空闲区间：一段位于 Vision Conv3D 与第一个 Vision Block 之间，另一段位于视觉 token 写入与第一个 Text Block 之间（如图 2 所示）。这两段空闲区间并非由大规模矩阵计算引起，而是源于 CPU 侧的 metadata 构造。

3.1 把每步动态 metadata 变成按签名复用的不变量

Qwen3-VL 需要根据 image_grid_thw 动态生成多类辅助信息，包括：

  • 位置插值的 index 与 weight；
  • Vision RoPE 的 position id 和频率表索引；
  • FlashAttention 使用的 cu_seqlens 与 max_seqlen；
  • 图像 token 在文本序列中的位置；
  • multimodal position id、rope delta 和 token type。

通用实现需要支持任意图像尺寸和序列形状，因此默认在每个 step 重新计算相关信息。但 GR00T-N1.7 训练中的图像预处理尺寸、spatial merge 规则和 batch 布局高度稳定，对相同 grid signature 重复构造 metadata 属于冗余操作。同时，构造过程中的 .item()、.tolist()、布尔归约和 H2D copy 会触发 host-device 同步，造成 GPU 主计算路径等待。

针对上述问题，我们设计了两级 metadata 缓存（如图 5）：

  • 在 batch 仍位于 CPU 时，按输入内容与 shape 生成 position metadata，避免数据搬上 GPU 后再做标量回读；
  • 在 CUDA Graph 准备阶段，按 grid_signature = ((T, H, W), ...) 构造 Vision metadata，并在 replay 时按静态张量的稳定 data_ptr() 绑定。

按内容建立缓存可避免相同输入的重复计算，按指针绑定则可避免 Graph replay 期间执行 Python 动态查找。当 grid、token 数或 attention mask 形状发生变化时，系统会校验 Graph 合约，无法安全复用的 batch 不会沿用已有 metadata。

3.2 跳过 action loss 未使用的 151,936 维词表投影

lm_head 用于将 Backbone 输出映射为语言词表 logits，而 GR00T-N1.7 训练只使用 hidden states 计算 action loss，并不消费语言 logits。因此，默认 forward 中的 2048 → 151936 词表投影对该模型属于冗余计算。针对这一冗余路径，我们在 GR00T-N1.7 训练中直接返回 Backbone hidden states 并跳过 lm_head；其他需要语言 logits 的任务仍保持原有 forward 行为。

3.3 融合 RoPE 与 Pointwise 计算，减少 Kernel 发射与中间张量

Profiler 中 vectorized_elementwise_kernel 每步调用 16,260 次；98 次 CatArrayBatchedCopy 里有 80 次来自 Vision/Text RoPE 的 rotate_half()。典型 PyTorch 实现如下：

def rotate_half(x):
    x1 = x[..., : x.shape[-1] // 2]
    x2 = x[..., x.shape[-1] // 2 :]
    return torch.cat((-x2, x1), dim=-1)

q = q * cos + rotate_half(q) * sin
k = k * cos + rotate_half(k) * sin

该计算在数学上仅包含旋转与乘加，执行时却会展开为 slice、neg、cat、mul、add 等多个 kernel，并产生中间张量和 layout copy。单个 block 中的开销有限，但在 24 层 Vision Block 和 16 层 Text Block 中重复执行后，其累计成本不可忽略。针对这种高频模式，我们为 Vision RoPE 与 Text RoPE 分别实现了 CUDA 融合 kernel，在一次 kernel 中读取 q/k/cos/sin，直接完成 half rotation 和乘加并写出结果。随后，我们又把冻结 Text Backbone 中的两类 pointwise 模式纳入融合（如图 5 所示）：

  • RMSNorm 保留原有 FP32 reduction 语义，在同一 kernel 内完成归一化收尾与权重缩放；
  • 合并 MLP 中的 SiLU(gate) * up，减少激活中间张量及一次逐元素遍历。

融合 kernel 不会无条件替换所有调用：当输入为 CUDA tensor，rank/shape 与 cos/sin dtype 均满足约束，且所有输入均不需要梯度时，才启用 fused path；Text Norm 和 MLP 同样需要校验连续性、dtype、device 与冻结状态。任一条件不满足时，均回退至 Transformers 原始实现。

4. 训练执行优化：重构迭代调度与分布式通信

算子融合减少了执行节点，但每个 step 仍包含大量 Python、dispatcher 和 CUDA launch 开销。继续优化单个耗时较短的算子，边际收益已经有限（如图 6 所示），此时需要从整体上调整迭代的执行方式。

4.1 选择 Full-Iteration CUDA Graph

在评估 CUDA Graph 时，我们没有将捕获范围限定在单个模块或 microbatch forward。对 GR00T-N1.7 而言，局部捕获仍会将训练循环划分为多个阶段：forward Graph 之外还包括 backward、DDP bucket AllReduce、梯度裁剪、optimizer step、输入复制和随机数准备。CPU 仍需在这些边界之间进行调度，跨阶段的小 kernel 也无法被完整固化，因此我们选择捕获完整训练迭代：

Forward
  → action loss
  → Backward + DDP AllReduce
  → grad norm / clip
  → AdamW step

在 capture 前，我们先完成 Eager warmup，物化优化器状态和稳定 grad buffer；随后为输入、输出、学习率、随机数与 Graph 结果分配地址稳定的 tensor。Graph replay 期间不再创建新的训练对象，只把下一批数据复制进静态 buffer，然后重放已经捕获的 CUDA 工作。

该方案的关键不在于调用 torch.cuda.graph()，而在于将原本依赖 Python 和动态 shape 的执行路径转化为稳定的 Graph 合约：

  • FlashAttention mask 处理不能在 capture 中执行 attention_mask.all() 或 max().item()，因此提前缓存 unpadding metadata；
  • 图像 grid、token 数、attention mask 和序列长度必须在 replay 前验证；
  • CPU 上采样的 flow-matching timestep 通过 pinned host buffer 和独立 stream 搬运，保持原随机数消费顺序；
  • CUDA generator 状态注册到 Graph，确保 dropout 与 action noise 的 replay 语义；
  • DDP AllReduce 留在 Graph 内，避免 capture 外重复同步。

4.2 利用冻结边界实现跨迭代 Backbone 前向

Full Graph 降低了 launch 碎片化，但反向末端仍存在难以完全隐藏的 NCCL 通信。GR00T-N1.7 的冻结结构提供了进一步优化的条件：batch n+1 的 Backbone 前向不依赖 batch n 的 optimizer 更新。

因此，我们进一步将完整执行图拆分为两个 Graph：

  1. Backbone Graph：只执行冻结 Qwen3-VL 前向，结果写入独立 staging buffer；
  2. Train Graph：读取稳定的 Backbone 输出，执行 Action Head forward、backward、DDP 通信、梯度处理和 optimizer。

在稳态流水中，Train Graph 正在处理 batch n 时，专用 Backbone stream 已经开始计算 batch n+1。Backbone 输出完成后，通过 event 建立生产者—消费者依赖，再拷贝到 Train Graph 的静态输入。与此同时，copy stream 继续预取 batch n+2。

该方案并未并行执行同一 batch 的前向与反向，因为二者存在真实的数据依赖。实际利用的是不同 batch 之间的无依赖区间，并通过冻结边界确保参数在两条流水之间不会发生版本错位。运行前还会检查 Backbone 所有参数的 requires_grad=False；一旦 Backbone 参与训练，该流水假设便不再成立。该方案不仅提前完成下一批的部分前向计算，也利用这段计算覆盖当前批次的一部分暴露 NCCL 通信。

4.3 覆盖暴露通信并减少梯度重复访存

在利用跨迭代 Backbone 流水覆盖部分通信后，进一步的优化重点转向 backward 之后的显存读写。传统路径中，同一份 gradient 至少经历三类额外操作：

  • 每次 replay 前，把 leaf grad buffer 清零；
  • Autograd 的 AccumulateGrad 再执行一次 grad += new_grad；
  • clip_grad_norm_ 用独立的 _foreach_mul_ 把裁剪系数写回全部 gradient，随后 AdamW 又完整读取一次。

对于地址稳定且每次仅包含一个 microbatch 的 Full Graph，上述内存操作可以进一步合并。我们在 capture 前物化所有 trainable parameter 的稳定 grad buffer；capture/replay 时由 backward 直接写入本轮梯度，避免"先写 0、再执行 add"。同时，梯度裁剪仅计算 global norm 与 device-side scale，不再单独写回缩放后的梯度。如图 7 所示，我们实现的 capturable AdamW 在首次读取 gradient 时完成 grad × scale，并直接更新一阶动量、二阶动量与参数。

总结

本次性能优化并非针对单一算子，而是围绕数据供给、模型计算与训练执行重新梳理关键路径，使原本间断的执行过程形成连续流水。最终，GR00T-N1.7 的训练吞吐从 58.44 samples/s/device 提升至 104.64 samples/s/device，达到社区实现的 1.79 倍加速。
